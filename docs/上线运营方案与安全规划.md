# 面包工厂 · 上线运营方案与安全规划

> 适用场景：把当前「单机演示版」升级为**联网、多设备、打通收银台与支付、真实运营**的店铺经营系统。
> 核心诉求：原料入库 → 配方核算 → 成品成本 → 收银结账 → 每月流水/成本/单品表现分析。
> 本文为**规划与分析文档**，不含代码。

---

## 0. 一句话结论

这是一次从「玩具」到「真实生产系统」的**质变**：需要从零搭建后端（服务器 + 数据库 + 账号 + 接口），并承担真实数据与资金带来的安全与合规责任。建议**分阶段**推进，先做最小可用版（多设备同步），再逐步加成本核算、硬件支付、上线加固。

## 1. 架构：从单机到云端

```
【现在 · 单机版】
  手机浏览器 ──> localStorage（数据只在本机，不联网）

【目标 · 运营版】
  平板(收银) ┐
  手机(老板) ┼──HTTPS──> 后端API ──> 数据库(云端，唯一真实数据源)
  电脑(报表) ┘                         │
                                       ├─ 每日自动备份(异地)
  收银硬件(打印机/钱箱/扫码枪) ─────────┤
  支付(微信/支付宝商户) ───────────────┘
```

关键变化：**数据从「各设备本地」搬到「云端唯一数据源」**，所有设备登录同一账号、共享同一份实时数据。

## 2. 功能模块清单

### 2.1 基础设施
- 后端服务（API）+ 关系型数据库（MySQL / PostgreSQL）
- 账号与权限：老板 / 店长 / 店员分级（店员看不到成本与利润）
- 多设备实时同步 + 并发冲突处理（多人同时改库存）

### 2.2 工厂 → 成本 → 结账 核心链路（你的差异化）
这是市面通用收银通常**做不好**的部分，建议作为系统核心：

```
① 原料管理      面粉/黄油/糖… 入库数量、采购单价、批次、保质期
② 配方 BOM      1个可颂 = 80g面粉 + 20g黄油 + 5g糖 + 人工/水电分摊
③ 生产/成品     按配方生产，自动计算「单个成品成本」并扣减原料库存
④ 销售结账      成品出售，记录售价、数量、支付方式
⑤ 报表分析      每月流水、毛利、各原料消耗、各成品表现/排行
```

### 2.3 数据模型（建议表结构草案）
| 表 | 关键字段 |
|---|---|
| users | 角色、密码哈希、所属店铺、状态 |
| materials（原料） | 名称、单位、当前库存、加权平均成本、保质期 |
| material_batches（进货批次） | 原料、数量、单价、进货日期 |
| recipes（配方/BOM） | 成品、原料明细(用量)、人工/分摊成本 |
| products（成品） | 名称、售价、当前库存、最新单位成本 |
| production（生产单） | 成品、产量、消耗原料、生成时间、成本快照 |
| orders（订单） | 明细、总价、成本、毛利、支付方式、操作人、时间 |
| audit_logs（审计） | 谁、何时、改了什么（改价/退款/改成本必留痕） |

### 2.4 收银与支付
- 硬件：小票打印机、钱箱、扫码枪、客显（依具体型号对接）
- 支付：微信支付 / 支付宝（需商户号）；每笔与平台流水**对账**

## 3. 技术选型建议（务实、低门槛优先）
| 部分 | 建议 | 说明 |

## 4. 安全隐患清单与预防（联网 + 真钱，按优先级）

### 🔴 P0 — 数据安全与可用性（最高）
| 隐患 | 后果 | 预防 |
|---|---|---|
| 数据丢失 / 勒索病毒 | 多年经营数据归零 | **每日自动异地备份 + 定期演练恢复** |
| 数据库暴露公网 | 被脱库 | 数据库不开公网、限 IP、强密码 |

### 🔴 P0 — 账号、权限、资金
| 隐患 | 后果 | 预防 |
|---|---|---|
| 账号被盗/暴力破解 | 数据泄露、被改 | 强密码 + 双因素 + 登录限次 |
| 越权（店员看成本/改价） | 利润泄露、内部舞弊 | **接口层做权限校验**，非仅界面隐藏 |
| 假结账/改价跑单 | 资金损失 | 关键操作审计日志 + 支付对账 |
| 支付密钥泄露 | 资金风险 | 密钥只在服务端、用密钥管理服务，不进前端/不进 Git |

### 🟠 P1 — 技术攻击面
| 隐患 | 预防 |
|---|---|
| SQL 注入 | 参数化查询、ORM、输入校验 |
| XSS / CSRF | 输出转义(已具备)、CSRF Token、CSP |
| 接口被刷 / DDoS | 限流、验证码、云高防 |
| 明文传输 | 全站强制 HTTPS / TLS |
| 依赖/系统漏洞 | 定期打补丁、依赖审计 |

### 🟠 P1 — 合规（中国大陆运营）
| 项 | 说明 |
|---|---|
| ICP 备案 | 大陆服务器对外提供服务的前提 |
| 个人信息保护法(PIPL) | 存会员手机号等需合规收集、加密、最小化 |
| 税务 / 电子发票 | 涉及开票需对接合规渠道 |
| 等保（视规模） | 规模扩大后可能涉及网络安全等级保护 |

### 🟡 P2 — 运维与内部
- 店员权限最小化、离职即停用账号
- 操作日志可追溯
- 监控告警（服务器宕机、异常登录、磁盘满）

## 5. 分阶段路线图

| 阶段 | 目标 | 主要交付 |
|---|---|---|
| **一、MVP** | 多设备共享同一份数据 | 后端 + 账号权限 + 云端库存/订单同步（暂不接硬件支付） |
| **二、成本核算** | 跑通工厂链路 | 原料→配方BOM→成品成本→经营报表 |
| **三、收银硬件** | 实体收银可用 | 打印机/钱箱/扫码枪 + 微信/支付宝 + 电子小票 |
| **四、上线加固** | 正式对外 | ICP备案、HTTPS、每日备份容灾、安全加固、压测 |

> 时间为粗估，受需求细节与是否兼职/全职开发影响很大，仅供参考：
> 一阶段约 2~4 周；二阶段约 2~4 周；三阶段强依赖硬件，1~3 周；四阶段 1~2 周。

## 7. 自建 vs 现成 SaaS 决策

| 路线 | 优点 | 缺点 | 适合 |
|---|---|---|---|
| **自建（在本项目上做后端）** | 完全贴合「原料→配方→成品成本」、数据自有 | 投入大、安全/运维责任自负 | 把精细成本核算当核心竞争力 |
| **现成 SaaS（美团/商米/思迅/银豹等）** | 上线快、有售后、合规省心 | 多数缺「生产/BOM 成本核算」，定制难 | 只想尽快正常营业 |
| **混合** | 日常收银用成熟产品，成本分析用本 App | 两套系统需手工/接口对账 | 想快又想保留特色分析 |

**建议**：若「原料成本→成品→每月流水/单品表现」的精细核算是你的核心诉求（通用收银确实弱），走**自建**，但务必分阶段；否则**现成 SaaS 带生产模块**上线最快。

## 8. 关键提醒（最容易踩的坑）
1. **备份是第一位**：上线第一天就要有自动备份，别等出事。
2. **权限在后端校验**：店员看不到成本，必须是接口层就拦住，不能只在界面藏。
3. **支付要对账**：每笔收款和平台流水对得上，关键操作留痕。
4. **密钥不进前端、不进 Git**：支付/数据库密钥只放服务端。
5. **先小后大**：先把多设备同步跑通，验证好用了再加硬件和支付。
6. **合规别忽略**：大陆对外服务先备案；存会员信息走 PIPL 合规。
